一、 今日最值得关注（Top 10）

1. MCP 协议史上最大重构：取消 Session，走向无状态
2026 年 7 月 28 日，Anthropic 发布 MCP 第五次大版本修订，移除协议层 Session 状态管理，使 MCP Server 真正支持 Kubernetes 水平扩缩容。
★★★★★ 技术价值 ★★★★★ 工程价值 ★★★★★ 企业价值 ★★★★★ 影响程度

这是 MCP 从「单机调试协议」变成「企业级生产协议」的关键一步。旧版有状态 Session 是阻止企业从试点走向万级 Agent 部署的首要障碍。新版让每个请求自带完整处理信息，任何实例都能接单，负载均衡不再是瓶颈。

直接解决了三个痛疾：Pod 重启丢会话、负载均衡粘性路由、K8s 水平扩缩容形同虚设。工程师不再需要为 MCP Server 设计特殊的状态持久化方案。

对企业 AI 平台建设的影响是根本性的——MCP 现在可以在生产环境真正跑起来，不再是 PoC 玩具。如果你的智能体平台依赖 MCP 做工具接入，这是必须关注的更新。

建议：立即学习。本周就应该研读新版 MCP 规范，评估现有 MCP Server 的迁移成本。特别注意幂等性设计——无状态下重试变得频繁，工具实现必须保证幂等。
2. 国产大模型「八周五连发」：DeepSeek 斩杀线正式形成
短短八周内，Kimi K3（2.8T）、Qwen3.8-Max（2.4T）、DeepSeek V4-Flash、GLM-5.2、Seedance 2.5 五款重量级模型密集发布，性能和价格双向碾压美国闭源模型。
★★★★★ 技术价值 ★★★★☆ 工程价值 ★★★★★ 企业价值 ★★★★★ 影响程度

中国模型已占据 OpenRouter 30% 流量。DeepSeek V4-Flash 以 0.03 美元/任务的成本取得 AI² Index 50 分（与 Gemini 3.6 Flash 持平），仅为 Claude Fable 5 价格的 1/100。这不是「追赶」，而是「另起赛道」。

Qwen3.8-Max 支持 1M token 上下文窗口和多日自主编程（16 天编码测试）；DeepSeek V4-Flash 原生支持 Responses API 并适配 Codex。国内企业选型的性价比天花板已被大幅抬高。

对国内企业 AI 平台建设意义重大：中等规模企业已有条件自主部署前沿级模型，不再依赖海外云厂商 API。但需注意：部分模型面临蒸馏/出口管制指控，合规风险需评估。

建议：立即学习。重点评估 DeepSeek V4-Flash 在企业 Agent 场景的接入方案，关注 Qwen3.8-Max 开源时间。
3. Claude Opus 5 发布：以 Opus 价格获得接近 Fable 5 的能力
7 月 24 日 Anthropic 发布 Claude Opus 5，定价维持 $5/$25（与 Opus 4.8 相同），但在 CursorBench 上仅落后 Fable 5 0.5%，成本仅为其一半。
★★★★★ 技术价值 ★★★★☆ 工程价值 ★★★★☆ 企业价值 ★★★★☆ 影响程度

Opus 5 引入了五级 effort 拨盘（low/medium/high/xhigh/max），单一模型可同时服务低成本高并发和昂贵长周期 Agent 两种场景。1M token 上下文 + 128K 最大输出。

effort 拨盘是真正的工程创新——同一模型可以根据任务复杂度动态调整推理深度，无需切换模型。这简化了 Agent 系统的模型路由逻辑。

如果你在 Agent 编程场景使用 Fable 5（$10/$50），Opus 5 提供了同价位更优选择。但需注意：Opus 5 使用新 tokenizer，同样文本多产生约 30% token，按 token 比价会低估实际成本。

建议：持续关注。建议在 Agent 编程场景小范围测试 Opus 5 vs Fable 5 的实际效果。

OpenAI GPT-5.6 系列 7 月 9 日 GA，7 月 30 日 Luna 降价 80%（$0.20/$1.20），Terra 降价 20%，Sol 新增 2.5 倍速 Fast Mode。

Luna 降价后输入价与上代 GPT-5.4 nano 持平，Agent 高频任务的调用门槛大幅拉低。对做大量分类、抽取、摘要的企业场景，成本结构已改变。

建议：持续关注。立即审查现有 GPT API 使用量和成本结构。
5. A2A 协议一周年：150+ 组织生产部署，Agent 通信标准化加速
A2A 协议庆祝一周年，宣布 150+ 组织生产部署（含 Microsoft、AWS、Salesforce、SAP、ServiceNow），v1.0 于 5 月正式发布，六种语言 SDK 就绪。
★★★★★ 技术价值 ★★★★☆ 工程价值 ★★★★☆ 企业价值 ★★★★☆ 影响程度

A2A 的核心设计——AgentCard（智能体名片）+ Task 对象携带完整生命周期状态——定义了 Agent 间发现、委托和协作的标准方式。与 MCP 分层：MCP 向下对接工具（Agent 的「手」），A2A 横向连接 Agent（Agent 的「嘴」）。

A2A 的 Task 状态机（submitted → working → input-required → completed/failed/canceled）天然适合企业级多 Agent 编排。Azure AI Foundry 和 Amazon Bedrock 已原生支持。

建议：持续关注。在多 Agent 协作场景中优先评估 A2A。

9. vLLM 0.26 vs SGLang 0.5.16：KV Cache 成为推理引擎新战场
7 月 25 日同一天，vLLM 0.26 和 SGLang 0.5.16 双双发布，目标都是解决 KV Cache 溢出 HBM 的问题，但采取了截然相反的路径。
★★★★☆ 技术价值 ★★★★☆ 工程价值 ★★★☆☆ 企业价值 ★★★☆☆ 影响程度

vLLM 0.26 引入对象存储二级缓存层，冷区块溢出而非丢弃；SGLang 0.5.16 将 UnifiedRadixTree 设为默认，GLM-5.2 DSA 场景下每 rank KV 内存降低 74%。两条技术路线代表了「换更多存储」vs「更聪明地用存储」的不同哲学。

建议：持续关注。RAG/知识库场景可优先评估 SGLang 的 RadixAttention。

九、 今天最值得学习的三个知识点

知识点 1：MCP 协议的无状态化重构

为什么需要

旧版 MCP 有状态 Session 导致：Pod 重启丢会话、负载均衡粘性路由、K8s 扩缩容失败。这阻止了 MCP 从 PoC 走向万级 Agent 生产部署。

是什么

新版 MCP 移除 initialize 握手和 Mcp-Session-Id，每个请求自带身份、能力、版本号。任何一个 Server 实例都能处理任何请求，普通的轮询负载均衡直接可用。

怎么使用

• 客户端：每次请求携带完整上下文，不再依赖 Session 状态
• 服务端：实现无状态工具函数，任何实例可接单
• 特别注意：幂等性是最大挑战——重试变得频繁，工具实现必须保证幂等

最佳实践

• 状态管理下沉到应用层（Redis/DB），不要依赖协议层
• 工具函数设计为幂等操作
• 上下文与任务进度由应用自行持久化

容易踩坑

• 幂等做漏了，重试会安静地多扣一笔钱
• 旧版 MCP Server 不兼容，需要适配迁移

推荐资料

MCP 官方 Release Note（2026-07-28）；《MCP 取消了 Session，也把状态这门生意让给了云厂商》

⏱ 学习时间：15 分钟即可掌握核心概念

知识点 2：Agent 协议栈的分层架构（MCP + A2A + AG-UI）

为什么需要

Agent 从「单机推理」走向「多机协同」，需要一个清晰的协议分层：怎么接入工具？怎么连接其他 Agent？怎么与用户交互？

是什么

三层协议分工：
• MCP = Agent 的「手」：标准化工具/数据/API 接入
• A2A = Agent 的「嘴」：Agent 间发现、委托、协作
• AG-UI = Agent 的「脸」：向用户展示推理过程和交互组件

怎么使用

• MCP：定义 Tools、Resources、Prompts 三类抽象
• A2A：通过 AgentCard（/.well-known/agent-card.json）暴露能力，Task 对象管理生命周期
• AG-UI：声明式描述 Agent 可渲染的 UI 组件（表单、图表、按钮等）

最佳实践

• MCP 管工具接入，不管会话管理
• A2A 管 Agent 间协作，不管具体工具
• 状态由上层（A2A Task 层或应用编排层）管理

容易踩坑

• 把 MCP 和 A2A 当竞争关系——它们是分层分工，不是替代
• 把状态管理放在 MCP 层——新版已明确这是应用层的职责

推荐资料

A2A 协议 GitHub（25000+ Star）；《从 MCP 到 A2A：Agent 间通信协议栈的分层演进与选型之争》

⏱ 学习时间：15 分钟即可建立协议栈全局视图

知识点 3：LangChain Deep Agents 架构模式

为什么需要

企业级 Agent 不是单次问答，需要：任务分解、工具编排、长期记忆、人工审批、状态追踪。Deep Agents 是 LangChain 对企业级 Agent 架构的系统化总结。

是什么

Deep Agents v0.7 提供了一套 Agent 架构模式：
• 任务分解与分配 • 长时间运行的 Agent 工作流 • 人工在回路（HITL）
• Agent 可观测性（LangSmith 集成） • 多 Agent 编排

怎么使用

使用 LangGraph 构建 Agent 状态机；通过 LangSmith Gateway 实现运行时控制和审计；参考 Stripe Kai 的实践案例

最佳实践

• Agent 不只是一个模型调用——是状态机 + 工具编排 + 人机协作
• 生产级 Agent 必须有：权限控制、成本追踪、审计日志
• 从「对话工具」升级到「生产力主体」需要完整的治理框架

容易踩坑

• 把 Agent 当成「更聪明的 Chat」——缺少状态持久化和人工审批节点
• 忽略 Agent 的 Token 消耗成本——长周期 Agent 的 API 费用可能远超预期

推荐资料

LangChain Blog: "How Stripe Built Kai"；LangChain Blog: "Building Governed Agents"

⏱ 学习时间：15 分钟了解架构全景
