# 技术趋势研判（Tech Trend Radar）

## Skill 简介

对目标 AI 技术进行结构化研判，通过联网搜索采集多源信号，从成熟度、商业价值、团队适配度、风险成本四个维度评估，给出技术雷达定位（Adopt/Trial/Assess/Hold）与可执行的行动建议，最终输出结构化研判报告。适用于技术选型决策、季度技术规划、团队技术方向对齐等场景。

## 使用场景

- **新技术选型决策**：判断某项技术是否值得团队投入学习
- **季度技术规划**：梳理本季度应关注、试验或采纳的技术方向
- **团队技术方向对齐**：用统一框架评估技术，避免凭直觉争论
- **投入资源论证**：为技术投入决策提供可解释的量化依据

## 输入

| 参数 | 必填 | 说明 |
|------|------|------|
| 技术名称 | 是 | 要研判的目标技术，如"MCP协议"、"Harness工程"、"小模型+工程补偿" |
| 业务背景 | 否 | 当前业务场景与痛点，提供后评估更精准 |
| 团队现状 | 否 | 团队技术栈、人员能力、系统架构，提供后适配度评估更准 |
| 关注维度 | 否 | 如特别关注某个维度（如成本/安全），可指定加权 |

## 输出

- **技术画像卡片**：五维度结构化事实卡片，含可信度标注
- **四维评分卡**：成熟度/商业价值/团队适配/风险，每项0-10分+依据链
- **技术雷达定位**：Adopt/Trial/Assess/Hold 四环之一+归置理由
- **行动建议清单**：含负责人角色、时间节点、预期产出
- **研判结论**：一段话总结，可直接用于汇报

## 工作流程

### Step 1：多源信号采集（联网搜索）

对目标技术进行五组关键词搜索：

- 组1：`{技术名} 论文 原理 最新进展`
- 组2：`{技术名} 开源 GitHub 生态`
- 组3：`{技术名} 行业报告 趋势 2026`
- 组4：`{技术名} 落地案例 生产环境 实践`
- 组5：`{技术名} 踩坑 问题 局限性`

每组取 Top3 结果，提取核心事实点，标注来源URL与时间。**如某组搜索结果不足3条，标注"信息不足"。**

### Step 2：信号降噪与结构化

对原始信号去重、降噪、可信度评估，按五维度整理为技术画像卡片：

- **技术原理**：核心机制、关键创新点
- **性能数据**：基准测试、对比数据、效率指标
- **落地案例**：谁在用、用在什么场景、效果如何
- **风险信号**：已知问题、兼容性、供应商风险
- **社区评价**：KOL观点、社区活跃度、采用趋势

每条事实标注可信度：高（官方文档/顶会论文）、中（知名技术博客/行业报告）、低（个人观点/单一来源）。

### Step 3：四维评估

基于技术画像，从四个维度评分（0-10分），**每项评分必须附带依据链**：

| 维度 | 评估要点 |
|------|---------|
| 成熟度 | 版本稳定性、API稳定性、Breaking Change频率、生态成熟度（第三方库/IDE支持/招聘供给）、生产级落地案例数量与规模 |
| 商业价值 | 能解决什么业务痛点、预期收益（效率提升/成本节约/体验改善）、与业务场景匹配度、可替代方案对比、不投入的机会成本 |
| 团队适配度 | 现有技术栈匹配度、学习曲线陡峭程度、所需人才储备、与现有系统集成复杂度。如未提供团队信息，按通用团队水平评估并标注假设 |
| 风险与成本 | 技术方向变更风险（被替代概率）、供应商锁定风险、合规与安全风险、投入沉没成本、维护成本预估 |

### Step 4：技术雷达定位

基于四维评分，按归置规则将技术定位到雷达四环之一：

| 环位 | 归置规则 | 含义 |
|------|---------|------|
| Adopt（采纳） | 成熟度≥7 且 价值≥7 且 风险≤5 | 生态成熟、风险可控，可直接在项目中使用 |
| Trial（试验） | 价值≥6 且（成熟度≥5 或 适配≥6） | 有明确价值但需验证，在非核心项目试用 |
| Assess（评估） | 成熟度<5 或 价值<6 | 值得关注但时机未到，跟踪观察 |
| Hold（暂缓） | 风险≥8 或 有明确更优替代 | 不建议投入，暂缓并记录理由 |

**边界处理：** 如评分处于两环交界，取保守环位（如Trial与Assess交界取Assess），并说明原因。

### Step 5：行动建议与报告生成

基于雷达定位生成具体行动建议：

- **Adopt** → 制定落地计划、培训安排、试点项目选择、推广路径
- **Trial** → 设计PoC验证方案、评估标准、时间节点、试点团队
- **Assess** → 指定跟踪人、复盘周期（如每季度）、重新评估触发条件
- **Hold** → 记录暂缓理由、替代方案推荐、重新评估条件

每条建议含：负责人角色、时间节点、预期产出。最终汇总为研判报告。

## Rules
1. 每条评分必须有依据链，禁止无依据打分
2. 信号来源必须标注URL和时间
3. 可信度低的信号不能作为评分核心依据
4. 如搜索结果不足，明确标注"信息不足"并降低对应维度置信度，不得编造
5. 雷达定位必须与四维评分逻辑一致
6. 行动建议必须具体可执行，禁止"建议持续关注"等模糊表述

## Constraints
1. 不做技术科普，假设用户有技术背景
2. 不写学术论文，聚焦决策支撑
3. 评分必须用数字（0-10），不用"高/中/低"
4. 报告总长度控制在3000字以内
5. 如用户提供业务背景，评估必须结合具体业务

### 输出示例

**技术画像卡片**

| 维度 | 核心事实 | 可信度 | 来源 |

| 技术原理 | Anthropic提出的开放协议，标准化LLM与外部工具/数据源的连接方式 | 高 | [官方文档] |
| 落地案例 | Claude Desktop、Cursor已接入，开源社区SDK覆盖Python/TypeScript | 中 | [GitHub] |

| 维度 | 评分 | 核心依据 | 置信度 |

| 成熟度 | 5/10 | 协议版本0.x，API未稳定，但核心设计已明确 | 中 |

| 团队适配 | 4/10 | 无.NET SDK，需自行封装或引入Python中间层 | 中 |
| 风险成本 | 6/10 | 协议可能变更，但开源可控，锁定风险低 | 中 |

**技术雷达定位**

- 定位：**Assess（评估）**
- 归置理由：商业价值高(8)但成熟度不足(5)且团队适配度低(4)，协议仍在迭代中，.NET生态支持缺失。建议跟踪观察，等待协议稳定和.NET SDK出现后再评估。

**行动建议清单**

| 序号 | 行动项 | 负责人角色 | 时间节点 | 预期产出 |
|------|--------|-----------|---------|---------|
| 1 | 指定1人跟踪MCP协议版本迭代 | 技术经理 | 即时 | 每月更新跟踪笔记 |

**研判结论**

MCP协议具有高商业价值，能直接解决Agent工具对接痛点，但当前成熟度不足（协议0.x版本）且.NET生态支持缺失导致团队适配度低。建议定位为Assess（跟踪观察），指定人员持续跟踪协议迭代与.NET SDK进展，待协议稳定后重新评估投入时机。

## 注意事项

- **信息不足处理**：如某维度搜索结果严重不足，对应评分置信度标注为"低"，并在研判结论中明确提示"该维度评估基于有限信息，建议补充信息后重新评估"
- **边界保守原则**：评分处于两环交界时取保守环位，宁可晚投不要早投
- **时效性提醒**：技术趋势变化快，研判报告有效期建议标注为3个月，过期应重新评估
- **团队适配假设**：如用户未提供团队信息，团队适配度按"通用中级技术团队"水平评估，必须标注此假设
- **不替代人工决策**：Skill 输出是决策参考，最终投入决策仍需技术经理结合实际情况判断

## 扩展建议

- **跨周期趋势对比**：存储每次评估的雷达快照，支持跨季度对比技术定位变化（升级/降级/新增/移除），自动检测趋势变化
- **批量研判**：支持一次输入多个技术方向，批量评估并生成技术雷达全景图
- **与「AI技术动态追踪」联动**：追踪Skill的每日动态可作为研判Skill的信号源输入，减少重复搜索
- **与「技术方案评审」联动**：研判结论的Adopt项可作为方案评审中的选型依据
- **团队适配度增强**：对接团队技能矩阵数据，实现更精准的适配度评估
